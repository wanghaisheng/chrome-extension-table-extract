# Pitch：面向论文列表的“表格/列表一键提取”浏览器扩展（CNKI / Google Scholar / PubMed）

## 1. 起点：一个很具体、很常见的痛点

研究人员、学生、情报分析、投研/咨询、图情工作人员在做文献调研时，通常会在 **CNKI、Google Scholar、PubMed** 等站点进行检索，然后需要把“论文列表”快速导出到：

- Excel / CSV（做筛选、去重、统计）
- SQLite（本地可检索、可回溯、可增量）
- 自己的知识库/脚本（进一步自动化）

现实问题是：这些页面的“列表”往往**不是标准 `<table>`**，或者只有局部是表格；并且分页、筛选、不同路径（pattern）之间结构变化很大，导致传统“只抓 table”很容易失败。

我们的目标是：**让用户只做一件事：打开页面 → 点开扩展 → 一键得到可用的数据（可预览、可保存、可全量导出）**。

---

## 2. 用户侧价值（Why users care）

### 2.1 一键把论文列表变成可用数据

- 对 CNKI：提取检索结果列表的标题/作者/单位/年份/引用/下载等字段，导出到 CSV 或保存到本地 SQLite。
- 对 PubMed：提取每条结果的标题、作者、期刊信息、PMID、引用/资源信息等。
- 对 Google Scholar：提取每条结果的标题、作者/来源摘要行、Cited by、Versions 等链接信息。

### 2.2 “看 20 行”和“导出全量”分离

预览只展示少量行，保证弹窗性能；但用户在复制/下载/批量导出时，默认拿到**完整行数**，避免“以为导出全量，实际被截断”的隐性错误。

### 2.3 本地优先：可追溯、可复用、可增量

把每次提取结果存到本地 SQLite：

- 可按 domain / url pattern / 时间过滤
- 可批量导出合并数据
- 可做备份/恢复（便于跨机器迁移、长期积累）

### 2.4 省心：同域只点一次，后续自动入库

用户第一次点击 “Add to SQLite” 相当于对该域名 opt-in；之后访问同域不同路径（不同 pattern）时，打开扩展即可自动保存，减少重复操作。

## 3. 技术侧亮点（Why this is hard, and what we did）

### 3.1 不只抓 `<table>`：结构化提取兜底（Structured Extraction）

针对“论文列表”这类页面，真实 DOM 更像“重复卡片/条目”，我们实现了结构化兜底提取策略：

- 支持 ARIA 语义表格：`role=table/grid/treegrid`
- 支持 `dl/dt/dd`（常用于属性列表、元信息对）
- 支持结构化 list（`ul/ol/li`）在具备“多列”特征时转表格
- 支持“重复卡片/文章列表”抽取成表格（例如 PubMed 的 `article` 列表、Scholar 的 `div.gs_r...`）

并且在策略上做了关键取舍：

- 仍然优先使用原有 `<table>` 抓取（兼容面更广）
- 但当页面只有“弱 table”（例如导航分页的 `<table>`）时，不让它阻塞结构化卡片提取

### 3.2 导出正确性：全量行、稳定顺序

导出/复制路径默认不再“隐式截断 20 行”，并且在存在序号/索引时保持从小到大稳定排序，尽量贴近用户在页面上看到的顺序与编号逻辑。

### 3.3 可靠性与可维护性：用 Playwright 做扩展级 E2E

把关键能力落到可回归的测试上（尤其是我们关心的站点形态）：

- `file://` 页面的友好错误提示（避免“Failed to fetch”让用户无从下手）
- Rows telemetry 缺配置时 fail-open（不影响核心功能）
- ARIA table / repeating cards / Google Scholar fixture 的提取回归
- SQLite opt-in + auto-capture 行为回归
- bulk export 的排序/合并回归

同时移除了 Puppeteer/Jest-Puppeteer 相关遗留，让测试栈统一为 Playwright（更贴近扩展场景）。

### 3.4 工程化：打包与依赖健康

- 提供 Chrome / Edge 打包脚本，直接产出 store 上传用 zip
- 保持 `npm audit` 可控（依赖升级/修复后不牺牲构建稳定性）

## 4. 开源二次开发视角（Why this fork matters）

这份工作不是“从零做一个采集器”，而是基于成熟的开源扩展工程做 **面向论文列表场景的二次开发**：

- 保留原项目对“表格/列表提取”的通用能力
- 通过结构化兜底提取 + 本地 SQLite + 自动入库，把它变成“可长期积累的研究数据工具”
- 通过 OpenSpec/WAL 的变更包管理与 E2E 测试，让演进可控、可审计、可回滚

这类 fork 的价值在于：

- 真实需求驱动：围绕 CNKI / Scholar / PubMed 的高频场景迭代
- 可复用性强：结构化提取能力能覆盖更多“非 table 的列表页面”
- 更适合本地化/企业内用：数据不必出网（SQLite / CSV），流程可内嵌到自己的知识库与分析管道

---

## 5. 合规与边界（务实说明）

- 扩展只在用户主动打开页面并触发时解析 DOM；本地存储是用户侧数据。
- 对站点的抓取策略以“解析可见 DOM”为主，不包含绕过登录/验证码等行为。
- 对 Google Scholar 等站点仍需遵守其服务条款与访问频率约束；我们更建议用于个人研究/小批量、且以“用户手动浏览触发”为主。

## 6. 可演示场景（Demo Script）

1) 打开 CNKI 检索结果页（确保页面显示 50 条）
2) 打开扩展 → 预览显示前 20 行
3) 点一次 “Add to SQLite”
4) 翻到同域另一个结果页/不同 pattern → 打开扩展 → 自动保存为 Saved
5) 打开 History → 批量导出 merged CSV → 行数与页面条目一致，顺序稳定
6) 打开 `tests/pubmed.html`、`tests/google-scholar-result.html`（fixture）验证结构化提取表格输出
