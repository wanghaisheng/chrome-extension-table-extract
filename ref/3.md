.codex/wal 目前的切入场景（什么时候触发）
在你们现在的流程里，WAL 是 Gate D：Context recoverability 的实现载体（见 .codex/core/pilot-promotion.md），触发点主要是：
非 trivial 的 change packet（BMM / 需要 change record 的 Quick）完成或阶段性收敛时
典型：openspec/changes/<change-id>/ 写了 README/design/tasks 并进入 closeout/归档。
出现“失败处理循环”时需要固化方法论变化
典型：某个验证反复失败，你调整了策略/方法（例如改验证方式、换批次策略、加锁解决并发），需要把“为什么这么改、证据是什么”写进 WAL，避免下次重踩。
跨会话/跨 agent 协作时
典型：多人/多 session 接力，WAL 用来传递“关键决策链 + 证据链接”，不需要回放长聊天。
对应你们模板里的硬约束是：openspec/changes/<change-id>/tasks.md Closeout 里要求 Pilot Gate D（WAL updated），并给出 .codex/wal/entries/YYYY/YYYY-MM-DD_<change-id>.json 路径。
WAL 会记录什么（为什么能帮你“出问题时找解法”）
WAL 条目（你们已建 schema + README + LIFECYCLE）核心是把“解决问题的路径”结构化成：
intent：当时要解决什么问题（避免后来误判动机）
decisions：关键决策与取舍（为什么选 A 不选 B）
actions：做了哪些动作（改了哪些面）
evidence：跑了什么验证/看到什么失败与修复证据（日志/测试结果/复现步骤）
links：链接到 change record、关键文件、测试、报告（避免 WAL 变大）
follow_ups：遗留风险/下一步
这意味着 WAL 并不是“再写一份文档”，而是把 失败→诊断→策略切换→验证证据 的链路保留为可检索的“短记录”。
遇到问题以后，如何借助 WAL 找潜在解决方案（实际用法）
当你遇到一个问题（例如：E2E flaky、WASM SQLite 崩溃、批量推广回归、某个 gate 失败），WAL 的使用路径通常是：
按 change-id 找：先看最近相关 change 的 WAL（同功能/同模块）
快速拿到：当时的 失败模式、采取的策略、哪些证据证明有效。
按 topic 找：如果你们维护了 topics/索引（你们已放了 index 占位），就按主题定位：e2e-flake / wa-sqlite / popup-ui / retention / governance 等。
按 file 找：问题落在某个文件/模块时，用 WAL 里的 links 回到“当时为什么这么写”，避免盲改。
输出形态通常就是“复用当时已经验证过的办法”：
直接复用当时的 调试手段（如何复现/如何观察/用哪些命令）
复用当时的 修复策略（例如加锁、加超时、改选择器、拆批次）
复用当时的 验证包（跑哪些测试能最快证明修复有效）
